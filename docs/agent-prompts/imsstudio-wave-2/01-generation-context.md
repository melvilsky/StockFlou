## Исходная проблема

В _generateAI целевые targetPath/targetId фиксируются до await. Но editorialForSave повторно читается из общего editorialStateProvider после ответа API. _toggleSelection меняет этот provider при выборе B. Следовательно, ответ для A может получить режим, город, страну и дату B.

Кроме того, чтение EXIF и геокодирование для A изменяют общий provider после await, когда инспектор уже может показывать B. В _generateBatchAI набор путей фиксируется, но userContext и editorialStateProvider читаются внутри работника Pool(3): очередь ещё не стартовавших элементов зависит от последующих действий пользователя.

В одиночной ветке есть setState/ref/context после await без полной проверки mounted; finally с mounted не защищает предыдущие обращения.

## Принятые правила

1. До первого await одиночной операции зафиксируй исходный id при наличии, точный path, настройки API/количество ключей, пользовательский контекст и копию Editorial: isEditorial, city, country, date. Сохрани текущие правила ограничения длины контекста и форматирования заголовка.
2. EXIF и геокодирование дополняют локальный контекст этой операции. Не записывай их промежуточные результаты в общий editorialStateProvider. Не вызывай setDate/setCity/setCountry для инспектора другого файла.
3. Итоговый заголовок, поля Editorial и editorial-тег рассчитываются по контексту этой операции. После ответа API не перечитывай общий provider для определения режима исходного материала.
4. Для серии зафиксируй список целей, общий режим запуска, пользовательский контекст и настройки до постановки задач в Pool. Все работники используют этот снимок. EXIF/геоданные конкретного файла остаются индивидуальными. Сохрани текущую семантику общего режима серии; не придумывай новый пакетный редактор.
5. AI-признак и пользовательские теги НЕ фиксируй старым снимком для последующей перезаписи. Как в предыдущей задаче, перед применением результата возьми актуальные теги исходного материала из filesProvider и передай их в tagsAfterMetadataGeneration. Изменение пользователем AI-признака во время запроса должно сохраниться.
6. Если исходная цель уже существовала, используй её id. Если локальный файл попал в каталог во время ожидания, переиспользуй запись с точно тем же path. Не бери id или теги текущего другого выделенного файла.
7. Инспектор обновляется только при mounted и совпадении исходной цели с текущей. Для существующей записи предпочтительно учитывать id и path; совпадение имени недостаточно. Если выбран B, ответ A может обновить каталог A, но не контроллеры и Editorial B.
8. Переход между файлами или папками при живом экране не отменяет результат для исходной цели. После фактического dispose экрана безопасно игнорируй поздние ответы: не обращайся к ref/context/setState/контроллерам и не запускай следующий API-запрос, диалог, запись в файл или БД. Уже начатая операция ввода-вывода может завершиться; это не основание продолжать цепочку. Не называй такую локальную защиту сетевой отменой.
9. Сохрани действующую логику подтверждения перегенерации и «Применить ко всем». Проверка жизненного цикла должна выполняться также после ожидания mutex и до показа очередного диалога.
10. Сохрани предел параллельности 3 и исключи повторный вход в генерацию, пока текущая серия выполняется. Освободи Pool после завершения принадлежащих ему задач, включая ошибки. Счётчики не должны зависеть от новой выбранной папки.
11. Ошибки обрабатываются без необработанных Future-исключений. Сообщение показывается только на живом экране. Завершение старой операции не сбрасывает состояние новой попытки, если такая попытка возможна.

## Границы

Не реализуй здесь устойчивые черновики, ревизии метаданных, сравнение ручных правок с AI, фоновые операции между уничтоженными экранами или глобальную отмену. Они потребуют общего каталога и отдельного решения. Снимок контекста решает подмену другим инспектором; не заявляй, что он защищает все ручные текстовые правки от перезаписи.

Не меняй в этом задании существующие правила workflowStatus и автоматической записи в оригиналы. Не расширяй форматы файлов. Не пытайся исправить все замеченные проблемы filesProvider за счёт скрытого дублирования его логики.

## Обязательные проверки

- A запускается как Editorial с городом A; выбирается B с другими значениями; ответ A сохраняет исходный контекст A, инспектор B остаётся прежним.
- Медленный EXIF или геокодирование A завершается после выбора B и не меняет provider B.
- A запускается без Editorial, затем выбирается Editorial B: ответ A не получает editorial-тег и поля B.
- В серии больше трёх файлов. После запуска меняется инспектор и контекст. Даже поздно стартовавшие работники используют параметры запуска; каждый получает собственные EXIF/геоданные.
- Во время запроса для A пользователь вручную меняет AI-тег A. Ответ сохраняет актуальный AI-тег и остальные пользовательские теги.
- Локальная цель появилась в каталоге, пока шёл запрос: используется существующий id, новая запись-дубль не создаётся.
- Dispose во время API, EXIF и ожидания диалога: нет обращений к уничтоженному UI, необработанных исключений, новых запросов или последующих записей.
- Ошибка одного файла не мешает завершению остальных; занятые ресурсы освобождаются. Диалог перегенерации по-прежнему последователен.
- Старые восемь тестов generation_tags продолжают проходить.

Запусти тесты своих двух папок, затем flutter analyze --no-pub. Не вызывай реальный AI API. Общий flutter test будет выполнен при совместной приёмке; если запускаешь его сам, учитывай, что другие чаты ещё могут менять свои файлы.
